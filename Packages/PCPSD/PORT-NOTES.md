# PCPSD — port notes

Native Swift port of photocraft's PSD/PSB format code (photocraft-psd, plus the PSD-specific parts of
photocraft-text and photocraft-io), MIT OR Apache-2.0, © ArtCraft Team and the PhotoCraft
contributors. PhotoDemon (`pdPSD.cls`, `pdPSDLayer.cls`, `pdPSDLayerInfo.cls`; BSD-2-Clause,
© Tanner Helland and contributors) was used as a cross-check for errata and colour-mode coverage.
Compositor v1.5 `Compositor/IO/PSD/` (MIT, © 2026 Wonder Assembly LLC) was used as a Swift
cross-check only. **No Compositor code was copied.** It has a PSD *reader* and a test-fixture writer
(`CompositorTests/PSDFixture.swift`) but no product writer, so it has no writer conventions to mine.
The headers that cite it say "no code copied". The structural spec is photocraft plus Adobe's
"Photoshop File Formats Specification".

The package is standalone. It depends only on Foundation, Compression, CoreGraphics and ImageIO (the
last in tests only). Build settings: Swift 6 language mode, tools 6.2, macOS 26. The clean build has
zero warnings.

## Type layers Photoshop cannot open (Photoshop 27.11)

The lead's Photoshop oracle found that a `TySh` whose EngineData lacks Photoshop's structures
**crashes Photoshop on open** (null dereference). Every one of the 474 type layers Photoshop opened
carried them. `PSDEngineData.photoshopStructureGaps()` (paths: `missingPhotoshopStructures()`;
also on `PSDTypeTool`) reports what is missing:

- **Crashes Photoshop** (`.crashesPhotoshop`):
  - `DocumentResources`.
  - `EngineDict.Rendered.Version` and `Rendered.Shapes.WritingDirection`.
  - Per shape: `Lines{WritingDirection, Children}`, `Procession`, and
    `Cookie.Photoshop.Base{TransformPoint0..2}`.
  - `EngineDict.AntiAlias` and `EngineDict.UseFractionalGlyphWidths`.
  - Each paragraph run's `ParagraphSheet.DefaultStyleSheet`.
  - A text descriptor with no parsable `EngineData` is reported as `EngineData`.
- **Photoshop refuses the file** (`.photoshopRefusesFile`): `ResourceDict.FontSet[].FontType` and
  `Synthetic`. With only the crash structures present, Photoshop stops crashing but still will not
  open the file.

`compatibilityIssues()` reports each case as an error with a named rule:

- `typeLayerEngineDataCrashesPhotoshop`, message prefix "PHOTOSHOP CRASHES ON OPEN".
- `typeLayerEngineDataBlocksPhotoshop`, message prefix "PHOTOSHOP REFUSES THE FILE".
- `typeLayerUnreadable`, for a `TySh` that does not parse.

Results:

- The corpus's 64 Photoshop type layers have 0 gaps, and no corpus file triggers the rules.
- A minimal third-party EngineData is flagged.
- Removing any single structure from a complete synthetic document is reported at its exact path.

### Type sizes Photoshop cannot read (`typeSizeOutOfRange`)

Photoshop 27.11 opens these files but loses the text (oracle RESULTS.md, TS; lesson AB-L-0262).
A 1e30 pt type layer opened as an empty pixel layer. A `Double.greatestFiniteMagnitude` one (size
and transform) raised the modal "Some of the type layers in this document were rasterized…".
`photoshopStructureGaps()` passes both files. The rule mirrors the oracle's pre-screen 3
(`Tools/PhotoshopOracle/Sources/PSOracleKit/TypeSizeScreen.swift`) and reports one issue per
type layer, listing the values:

- **What it checks:**
  - a style run's or style sheet's (`ResourceDict`, `DocumentResources`) FontSize outside
    0.01–1,296 pt;
  - a style run's effective size outside that range: FontSize × the transform's scale √|det|,
    checked only when the FontSize itself is in range;
  - a `TySh` transform component that is not finite or is beyond ±300,000.
- **Error** ("PHOTOSHOP RASTERIZES THE TYPE LAYER", no refusal prefix) for the measured classes:
  any non-finite value, or a size (FontSize or effective) of 1e6 pt or more.
- **Warning** otherwise. The 0.01 / 1,296 / 300,000 bounds are Photoshop's documented limits, not
  measured, and a transformed layer can legitimately go past 1,296 pt effective.
- **Code:** `PSDTypeTool.typeSizeViolations()` (TextRequirements.swift) and
  `PSDFile.typeSizeIssue` (Compatibility.swift).
- **Calibration:**
  - 0 hits on the ps-corpus (153 files, 10 type layers), the Unity corpus (36 files, 64 type
    layers) and the 150 `pcpsd-fixtures`.
  - In `ps-oracle/pcio-snapshot-c2` (1,333 files, 618 type layers) it flags the same 5 files as
    the pre-screen:
    - `hostileTypeSizes…` ×4: `08e3aaeee0` (1e30 pt) and `6639470508` (1.8e308) are errors, the
      two measured cases. `e3a378b9c9` (12 pt × scale 1e12, never opened) is an error by the
      ≥ 1e6 pt definition. `7eca2591d2` (12 pt × 1,100 = 13,200 pt) is a warning.
    - `textLayerRoundtripWithTySh-7f7ce94a65`, layer 41 (0 pt), is a warning.
  - It also agrees with the pre-screen on the first sweep's `pcio-snapshot` (4 files) and on
    `pcio-exports` (5).
- **Tests:** `TypeSizeRuleTests`, and the ps-corpus in `PSCorpusTests.measuredRulesHaveNoFalsePositives`.
- **PCIO:** `MapsTestKit.export` asserts that the linter reports no errors on every export
  (`MapsTestKit.swift:264`). So `PSDTypeBoundsTests.hostileTypeSizesWithoutPixelsImportWithoutAHugeRender`
  now records 3 issues, one for each error-class hostile size (1e30, 1.8e308, scale 1e12). This
  is expected. PCIO's owner can pass `knownLintIssue:` or skip `.typeSizeOutOfRange` there.

## Bugs found by the Photoshop oracle (Tools/PhotoshopOracle/RESULTS.md)

All four are fixed and tested against the 153-file ps-corpus. That corpus rewrites byte for byte
153/153.

- **F1, matte block order (Photoshop refused the file; all 32 builder rejects).**
  - Photoshop writes 16/32-bit layers with an empty `Mt16`/`Mt32` *first*, then `Lr16`/`Lr32`
    with a **positive** layer count. Its 8-bit files keep a negative count in the section and have
    no matte block. Seen in transparent-grayscale-16, transparent-rgb-16 and transparent-rgb-32.
  - The builder now writes exactly that.
  - The new linter rule `layerInfoBeforeMatteBlock` (error, "PHOTOSHOP REFUSES THE FILE") flags a
    layer-info block placed before its matte block.
- **B1, `SoFi`.** The colour-overlay key was misspelled `Sofi`, so overlays were dropped.
  - Every `lfx2`/`lfxs`/`lmfx` key in the ps-corpus is now known.
  - Overlays are read in the four files whose trees differed from Photoshop's reading.
  - `lrFX` keeps its legacy lowercase `sofi`.
- **B2, `Txt2` literals.** Photoshop's `Txt2` has 8-bit bit-flag strings, such as `/2 (0100…)`
  and `/3 (01110)`, which were rewritten as UTF-16.
  - `PSDEngineData.Entry` now records `stringEncoding` (`.eightBit`) for a dictionary value parsed
    from an 8-bit literal, and both writers keep it. `==` ignores it.
  - Result: `Txt2` round-trips 10/10, and the Unity corpus's 13/13 still pass.
  - Literals that are array elements are always written as UTF-16. Photoshop's files have none.
- **B3, user mask.**
  - `PSDLayerView.userMask()` now returns channel −3 when present. Otherwise it returns −2 only
    when the mask record lacks the "came from rendering" flag (bit 3).
  - A vector mask's rasterisation is available separately as `vectorMaskRendering()`.
  - ps-corpus: 100 raster, 2 vector-only and 2 both.
- **F2 (fixtures).** `PSDTestGen` writes HDR toning colour-mode data at 32 bits.
  - The linter rule `hdrToningMissingAt32Bit` (error, "PHOTOSHOP REFUSES THE FILE") flags a 32-bit
    model without `hdrt`.
  - `PSDFile.write` substitutes the default toning data for any 32-bit model whose colour-mode
    data is not `hdrt`. That data is never meaningful at 32 bits.
  - So every PCPSD write of a 32-bit file carries `hdrt`: builder output, and `serialized()` of a
    hand-built or modified model. Photoshop's own 32-bit files keep their bytes (153/153). F3, Duotone
  placeholder data, still needs a real duotone specification.

## Blend modes Photoshop accepts (Photoshop 27.11)

Photoshop refuses a file whose layers use a blend mode the document's mode and depth cannot have.
It raises a modal for pass-through on a record that is not a group. The oracle measured this
table with a new-document probe on Photoshop 27.11.0, 2026-10-12. It gave 0 false positives on 153
Photoshop-authored files, the 36 Unity files and 151 fixtures.

| Document | Layer modes allowed | Excluded |
|---|---|---|
| RGB 8/16, CMYK 8/16 | 27 (all) | — |
| RGB 32 | 15 | Color Burn, Linear Burn, Screen, Color Dodge, Overlay, Soft/Hard/Vivid/Linear/Pin Light, Hard Mix, Exclusion |
| Grayscale 8/16 | 21 | Darker Color, Lighter Color, Hue, Saturation, Color, Luminosity |
| Grayscale 32 | 9 | All of the RGB 32 and Grayscale 8/16 exclusions (allowed: `norm diss dark mul  lite lddg diff fsub fdiv`) |
| Lab 8/16 | 19 | Darken, Color Burn, Lighten, Color Dodge, Difference, Exclusion, Subtract, Divide |
| Bitmap, Indexed, Multichannel | none (no layers) | — |

- **Groups:** pass-through is valid on groups only, at every mode and depth. Otherwise groups
  follow the layer set.
- **Unmeasured combinations** (Duotone, and depths a mode does not have) are treated as
  unconstrained, except that pass-through stays group-only.
- **API:**
  - `PSDBlendMode.allowedModes(mode:depth:isGroup:)`, `isAllowed(_:mode:depth:isGroup:)` and
    `blendTableIsMeasured(mode:depth:)`.
  - `nearestAllowed(_:mode:depth:isGroup:)` gives the closest mode in the same family (darken,
    lighten, contrast or difference), else Normal.
  - A test checks the table against the oracle's `$PHOTOCRAFT_FIXTURES/ps-oracle/blend-table.json`
    (560/560 combinations; skipped when absent); `PCPSD_BLEND_TABLE` overrides the path.
- **Linter errors:**
  - `blendModeInvalidForDocument` ("PHOTOSHOP REFUSES THE FILE") checks the record's mode and a
    folder's `lsct` mode.
  - `passThroughOnNonGroup` ("PHOTOSHOP RAISES A MODAL").
  - Both skip layerless modes, which the existing "no layers" warning covers.
- **Builder:** `blendModePolicy` defaults to `.substituteNearest`. The builder writes
  `nearestAllowed` and adds a warning to the built file's `warnings`. `.refuse` throws, and
  `.keep` writes the mode as given, for negative fixtures. PCIO has no handling yet; it can call
  the same `nearestAllowed` to match.
- **Test fixtures:** `PSDTestGen` maps its blend modes through `nearestAllowed` by default.
  `invalidBlendModes: true` restores every key as given, for fuzzing. PSDTestGen remains a stress
  generator in other respects, such as odd block lengths, ZIP at 32 bits, and no `hdrt`.
- **Results:** the corpus (478 records) has 0 hits. Every excluded combination is flagged on layers
  and groups (2 × 58, plus 10 pass-through layers), and nothing else is.

## Layer blocks are 4-aligned

The Adobe spec only says lengths are rounded to even. Photoshop itself zero-pads every layer
tagged block to a multiple of 4 *inside* the length: 12,949 of 12,949 blocks across the 153
Photoshop files and the 36 Unity files, and 6,045 of 6,045 in this corpus. It enforces this at
least for `grdm`. Photoshop 27.11 refused a 126-byte gradient map and opened it with 2 zero bytes
added; its own `grdm` stores 162 bytes as 164.

- **Linter:** `layerBlockNotFourAligned` is an error for `grdm` ("PHOTOSHOP REFUSES THE FILE") and
  a warning for other layer blocks. The corpus has 0 hits.
- **Generating paths pad:** `PSDTaggedBlock.fourAligned(key:data:)` and `fourAligned()` do it.
  `PSDBuilder` pads its own blocks and the caller's extra blocks, and so do
  `PSDAdjustment.taggedBlock(key:)` and `PSDFillSetting.solid`.
- **Preserved blocks** read from a file stay byte-identical (36/36). Typed `serialized()` stays
  lossless, so wrap it with `fourAligned` when writing a new block.

## Placed layers, linked files, fills and vector masks (Photoshop 27.11 bisect)

The oracle bisected PCIO's last refusal families in Photoshop 27.11 (RESULTS.md, the C′ bisect and
C″). Each family opened as soon as one edit was made. All four are hand-built or damaged test
fixtures, not PCIO writer output. The rules are in `Compatibility.swift` (see the rule doc
comments).

**Errors**, with the prefix "PHOTOSHOP REFUSES THE FILE":
- `placedLayerWithoutLinkedData`. A `SoLd`/`SoLE` that holds only `Idnt` and `Trnf`, and whose
  unique id no linked-file item carries (`placedLayerBlocksKeepTheirKeys`; deleting that record
  opens the file).
  - The id is read from each item's bytes, so an item with the wrong kind label still counts.
  - The bare descriptor is required, because Photoshop opened a placed layer whose full
    descriptor named no linked item (a missing link, the sibling of
    `independentUnavailableLink…`).
  - Every `SoLd` Photoshop wrote (9 in ps-corpus, 98 in Unity) carries `placed`, `Type`,
    `Sz  `, `Rslt` and the rest.
- `placedLayerDataUnreadable`. A `PlLd`, `SoLd` or `SoLE` that fails `checkStructure`
  (`textShapeSmartRawBlocksSurvive`'s 4-byte `PlLd`, exactly). It replaces the generic
  "block PlLd: …" error.
- `linkedFileKindMismatch`. A `lnk2`/`lnk3`/`lnkD`/`lnkE` item that does not read strictly as
  its own kind but does as another (`independentUnavailableLink…`: `liFD` items relabelled
  `liFE`; restoring `liFD` opens the file).
- `fillLayerDataUnreadable` for a `SoCo` that is empty or does not parse. The oracle settled
  `vectorRenderedMaskNotDoubledOnShapes-4e72e7e793`:
  - B2 opened: a real 112-byte `SoCo`, with the 8-byte version-0 `vmsk` kept.
  - B3 was refused ("open options are incorrect"): the 0-byte `SoCo` kept, with a real `vmsk`.

**Warnings:**
- `fillLayerDataUnreadable` for `GdFl`/`PtFl` (not measured). One rule name carries two
  severities, so a screen keyed on the name alone should also check `severity == .error`.
- `vectorMaskWithoutPaths`: a `vmsk`/`vsms` with no path records. Photoshop opens them (8- and
  12-byte version-0 forms, and 8-byte disabled ones) and reads them as no vector mask, but never
  writes one (217/217 have records).

**Calibration:**

## Patterns in Photoshop's layout (requested by PCIO)

PCIO found that Photoshop 27.11 refuses files whose pattern data puts transparency in the *user
mask* array. photocraft (`patterns.rs:383`) and PCPSD wrote it there; PCIO rearranged PCPSD's bytes
meanwhile (`PatternMap.photoshopBlock` / `photoshopPatFile`, now a no-op).

- **Array layout** (`PSDPattern.write`, `Patterns.swift`): 24 channel slots, the user mask
  (slot 24) left empty, and transparency in the *sheet mask* array (slot 25 = count + 1), as in
  all 23 transparent patterns of the 312 Photoshop 2026 ships. Both the block and `.pat` writers
  use it. The reader takes the first written array after the colour channels as transparency, so
  slot 24 and slot 25 read the same; it records the slot it came from.
- **Indexed patterns:** the 4 bytes after the palette are `PSDPattern.paletteTrailer`, read and
  written back. Photoshop writes `01 00 00 ff` in 25 of the 26 indexed presets and in the
  ps-corpus pattern, and `00 83 00 82` in one (probably the colour count and the last index). A
  new indexed pattern defaults to `PSDPattern.photoshopPaletteTrailer`. `nil` writes no trailer,
  which is how some third-party files are laid out.
- **Stored arrays:** re-encoding cannot reproduce Photoshop's patterns. Its PackBits runs differ
  from `PackBits.encode`: all 946 rows of "Tree Tile 4" do, and re-encoding makes its 557,596-byte
  block about 8 KB smaller. Its presets also store 542 of 668 colour arrays raw. So a read pattern
  keeps each array's compression and payload, and `write` reuses them while the plane, depth and
  size are unchanged. They are not part of `==`. A plane that has changed is encoded again, RLE
  at 8 bits and raw otherwise.
- **Results:**
  - ps-corpus "Tree Tile 4" (`fill-pattern.psd`, `fx-pattern-overlay.psd`; indexed, 946², RLE)
    rewrites byte for byte through the model, and so does the whole file.
  - All 312 Photoshop 2026 preset patterns rewrite byte for byte (7 `.pat` files, read only).
    Two of the files append an `8BIMphry` preset hierarchy, which `PSDPattern` does not keep.
- **`PSDTestGen.small`** now carries Photoshop's empty `Patt` (length 0) instead of `01 02`.
- **Linter:**
  - `patternTransparencyInUserMask` is an error, "PHOTOSHOP REFUSES THE FILE". It fires when a
    pattern writes the user mask array.
  - `patternDataUnreadable` is an error for a `Patt`/`Pat2`/`Pat3` block that does not parse.
    The oracle has not isolated this as a cause, so the message has no refusal prefix.
  - Bytes after the last pattern that are not zero padding only get a warning. Photoshop opened 6
    PCIO exports whose `Patt` was the old `01 02` placeholder; it stops before a tail shorter than
    a length word, as PCPSD's reader does.
- **Calibration:**
  - ps-corpus: 0 hits in 153 files, which hold 145 pattern blocks (143 empty, 2 with
    "Tree Tile 4").
  - Unity corpus: 0 hits in 36 files with 36 empty `Patt` blocks.
  - The oracle's sweeps of PCIO exports, read 2026-10-12 at about 20:35 while the second sweep
    (`pcio-c2`) was still running:
    - All 40 files Photoshop refused for pattern data are flagged, all with transparency in
      slot 24: 16 `Patt`, 12 `Pat2`, 12 `Pat3`.
    - None of the 2,064 files it opened (1,076 + 988) is flagged.
    - It opened all 33 exports with transparency in slot 25 (17 `Patt`, 16 `Pat2`). PCIO's
      rearranged bytes are what PCPSD now writes itself.
    - With the same key and an 8-bit document, `Patt` was refused 16/16 in slot 24 and opened
      17/17 in slot 25.
    - Not yet seen by Photoshop: a transparent pattern in `Pat3` (32 bits) in slot 25.
- **Tests:** `PatternLayoutTests` covers both slots, the trailer, stored arrays, both rules, the
  generator, the Unity corpus, the presets and the oracle verdicts.
  `PSCorpusTests.photoshopPatternsRewriteByteForByte` and `measuredRulesHaveNoFalsePositives`
  cover the ps-corpus.
- **PCIO:** it builds unchanged (`swift build --build-tests`), and its rearranging step is now a

## Changes requested by PCIO

All of these are additive and source-compatible. PCIO builds against them unchanged.

- **NaN fixed point:** `PSDFixed.fromDouble(.nan)` is 0. Infinities saturate. Resolution and
  gradient-stop encoders no longer trap on NaN.
- **Linked-file names:** `PSDLinkedFile.embedded` writes the file name NUL-terminated with the
  terminator counted, as all 86 corpus items do. `strictInfo` / `parsedInfo(strict:)` give the
  strict reader (photocraft `check_embedded_item`: known type, version 1–16, open-descriptor flag,
  data inside the item). 86/86 corpus items read strictly.
- **Block signatures:** the block reader accepts `MIB8` / `46B8` beside `8BIM` / `8B64`, as
  photocraft's `is_sig` does. `PSDTaggedBlock.isBlockSignature`, `isForeignOrderSignature` and
  `isForeignOrder` are public. The linter errors on foreign-order blocks.
- **Public readers and writers:**
  - Tagged blocks: `PSDTaggedBlock.readBlocks(_:version:alignment:)`, `serialize`, `serialized(version:)`.
  - Layer records: `PSDLayerRecord.readRecord(_:version:)`, `serializedRecord(version:)`, `legacyName`, `decodedLegacyName`.
  - Masks: `PSDLayerMask(bytes:)`, `serialized()`, `storesRealBeforeParameters`.
  - Layer info: `PSDLayerInfo(body:version:)`, `serializedBody`, `serializedUnpaddedBody`.
  - Resources: `PSDImageResource.readBlocks(_:strict:)`, `serialize`, `serializedBlock()`, `resourceSignatures`.
- **Test support:** the `PCPSDTestSupport` product (`PSDTestGen`, `PSDSeededRandom`), built on the
  public API only. It compiles in release.
- **Patterns** (see above): transparency in the sheet mask array; the indexed palette trailer
  kept; `PSDTestGen.small` with Photoshop's empty `Patt`; the `patternTransparencyInUserMask` and
  `patternDataUnreadable` rules. Additive API: `PSDPattern.paletteTrailer`,
  `photoshopPaletteTrailer` and a defaulted `paletteTrailer:` initializer argument.

## Photoshop-acceptance rules the writer applies

These follow photocraft `builder.rs`, refined from the corpus:

- Layer info is padded to a multiple of 4 in both placements.
- 16-bit layers go into a global `Lr16` block and 32-bit layers into `Lr32`, with an empty section.
- 32-bit files carry `hdrt` colour-mode data (photocraft #291).
- Partially transparent composites write `Mt16`/`Mt32`, and RGB/Gray merged data is matted against
  white.
- Merged data defaults to RLE.
- Files have 1005 at 72 dpi, IPTC 1028 and print 1082. Without 1028 + 1082, ImageIO mislabels alpha.
  Version info 1057 is also written.
- Raster records: flags 0x08, block order `luni lnsr(layr) lyid clbl infx knko lspf lclr fxrp`.
- Group records: flags 0x18, `luni lnsr(lset) lyid lsct lspf lclr fxrp`. The folder `lsct` is 16
  bytes with sub-type 0. Groups have four raw empty channels.
- Blending ranges have cc+2 entries (40 bytes for RGB).
- Empty channels are always written raw.
- ZIP at 32 bits is written predicted, because Photoshop reads code 2 at 32 bits as predicted.

## Errata handled beyond photocraft

- Lenient resource section: an unparsable tail is kept raw, with a warning.
- Length-1 channels are kept raw.
- PSB long-length keys: a probe fallback (`longLengthOverride`) handles writers that disagree with
  the long-key table.
- Malformed data is salvaged where possible:
  - RLE salvage ignores a bad count table and clips overflow.
  - zlib decoding is lenient about trailing pad and missing Adler-32 (the checksum is still verified
    when present).
  - At 32 bits, ZIP data is checked for plausibility, with a fallback between predicted and plain.
- Mask records order real-before-parameters (#949).
- CS2 smart objects that have only `PlLd` now resolve (#2465), and linked items without the open
  flag still read.
- `Mtrn`/`Mt16`/`Mt32` are honoured for merged alpha.
- `lsdk` is read as `lsct`.
- EngineData parsing skips junk before `<<`.

ImageIO quirks found:

- The white matte is kept in 8-bit RGB merged data. 8-bit gray is unmatted, and 16-bit data returns
  as stored.
- The premultiplied-alpha label appears only when 1028 + 1082 are present.
- ImageIO's own writer has errata. In rgba8 files, 3 RLE layer channels have the first 8 bytes of
  row 0 clobbered. In rgba16 files, 4 ZIP+prediction layer streams cannot be decoded. ImageIO itself
  reads only the merged image.
- Lab, Indexed and Multichannel PSDs cannot be opened at all.

## Known gaps

- `tiff.rs` (layered-TIFF `ImageSourceData` transcoder, 2.3k lines) is not ported here. PCIO ports
  it (`PCIOFormats/TIFFSVG`) on top of the public readers above.
- PCPSD's own tests do not drive Photoshop; the separate oracle agent does. The type-layer rules
  come from that agent. Writer acceptance here rests on ImageIO, round trips and record shapes
  that match the corpus. Lab output cannot be checked by any native reader.
- The corpus is all RGB 8-bit. Photoshop's record conventions for the other modes were not
  observed; the builder applies the cc+2 blending-range rule to them by extension.
- Some blocks are typed for reading only:
  - `lrFX` (legacy effects) is typed but rewritten from its raw entries.
  - Edited slices re-serialize as v6. Untouched v7/v8 slices are kept byte-exact.
  - `fxrp` and `sn2P` have no typed view.
- Colour-managed output (CMYK/Lab/ICC) goes through CoreGraphics only. It is not compared to
  PhotoDemon's LittleCMS results.
- The builder writes RGB/Gray at 8/16/32 and CMYK/Lab at 8/16. It does not write Indexed,
  Duotone, Bitmap or Multichannel; the reader handles all of them.
- Mapping into PCDocument is not done here; that is another porter's package.
- Patterns:
  - Arrays that are new or changed are encoded with PCPSD's choices (RLE at 8 bits), not
    Photoshop's (mostly raw colour channels, RLE transparency). Photoshop opened both.
  - `.pat` files: an appended `8BIMphry` preset hierarchy is neither read nor written.
  - Patterns embedded in smart objects are not linted.

## Not possible natively

- Running Photoshop inside `swift test`. The Photoshop oracle is a separate tool.
- Using ImageIO as an oracle for Lab, Indexed or Multichannel PSDs.
- A bit-identical LittleCMS match.
